# ADR 0003: Application secrets via External Secrets Operator + Secrets Manager

- Status: accepted
- Date: 2026-11-24

## Context

Services need LLM API keys, database credentials and the cache AUTH token. We
want the following:

- no secret values in Git, Helm values, CI variables or Terraform variables;
- rotation without redeploying charts;
- a per-service least-privilege boundary.

## Options

1. **Kubernetes Secrets created by CI** (`kubectl create secret`). Secrets end up in CI logs and variables, rotation is manual, and Git doesn't record what exists.
2. **Secrets Store CSI driver.** Secrets are mounted as files and synced to env only through an extra sync step. Every pod needs a CSI volume, which conflicts with our read-only, minimal pod spec.
3. **External Secrets Operator (ESO) with AWS Secrets Manager.** ESO reconciles an `ExternalSecret` CR into a native Secret on a `refreshInterval`, and the app consumes it via `envFrom`.

## Decision

Use **ESO** with a `ClusterSecretStore` named `aws-secrets-manager`, authenticated
by EKS Pod Identity. `charts/service` renders an `ExternalSecret` when
`externalSecret.enabled=true`:

```yaml
externalSecret:
  enabled: true
  data:
    - secretKey: LLM_API_KEY
      remoteRef: { key: platform/prod/demo-api, property: llm_api_key }
```

Infrastructure-owned secrets are created by AWS, not by humans:

- RDS master credentials: `manage_master_user_password = true`, rotated by RDS (output `master_user_secret_arn`).
- Cache AUTH token: generated by Terraform and stored in Secrets Manager (output `auth_secret_arn`). It also exists in Terraform state, which is why the state bucket is KMS-encrypted, versioned and TLS-only.

## Consequences

- ESO is a tier-0 dependency: if ESO is down, existing Secrets keep working but new keys and rotations stall. It runs on the system node group with a PDB.
- The ESO IAM role gets `secretsmanager:GetSecretValue` scoped to the `platform/<env>/*` prefix plus the specific RDS/cache secret ARNs.
- Pods restart on rotation only when they read secrets at startup. Long-lived connections (Postgres) should re-read credentials on auth failure. Prefer IAM database auth for service users (enabled on the instance) and keep the master user for migrations only.
